> 논문의 "설계 결정의 근거"와 주간 발표의 "이번 주 배운 것"에 그대로 씁니다.
> GAN·판정 규칙 실험의 실패(E1 붕괴, D1·D4 버그 등)는 [RESEARCH_NARRATIVE.md](RESEARCH_NARRATIVE.md)에 자세히 있고, 여기서는 요약만 합니다.

## 출처 등급 (모든 기준값에 붙임)

| 등급 | 뜻 |
|---|---|
| **원문** | 표준이나 논문 원문에서 직접 확인함 |
| **문헌 간접** | 관련 문헌 근거는 있지만 그 숫자를 그대로 쓰지는 않음 (예: 1~4 cpd 근거로 1~10 cpd 범위를 씀) |
| **구현 선택** | 문헌에 숫자가 없어 우리가 정함. 바꾸면 결과가 어떻게 달라지는지 기록해야 함 |
| **미확인** | 출처를 아직 찾지 못함 |

## A. 연구 설계의 실패 (논문에 쓸 것)

### A1. GAN이 오라클의 평균판으로 붕괴 (11-05, 실험 E1)
- **증거**: z만 바꿨을 때 깜빡임 세기 표준편차 0.0004 (이상적이면 약 0.2). 세기 오차 0.18~0.19는 상수 하나로 맞힐 때의 이론 오차 0.175와 같음 (커밋 `e916988`)
- **원인**: 오라클 결과를 정답으로 따라 하게 하면 평균이 최적. Barbu 구현자 학위논문의 "매우 결정적"이라는 서술과 같은 현상
- **대응**: 목표를 오라클이 아니라 판정 규칙으로 바꿈(E2). 자세한 내용은 RESEARCH_NARRATIVE §3~4
- **배운 것**: 재구성 손실로 다양성을 기대할 수 없다. 다양성은 명시적으로 요구해야 한다

### A2. 화면 평균 밝기로 판정하면 국소 깜빡임을 놓침 (11-08)
- **증거**: 처음 만든 `measure.py`는 화면 평균 밝기 변화로 셌음. 화면 25%짜리 패턴이 깜빡이면 평균은 그 변화의 약 4분의 1만큼만 움직여 위험을 놓칠 수 있음. IRIS도 같은 약점이 있음(작은 영역 깜빡임 36개 중 3개만 검출, 커밋 `379e02b`)
- **대응**: 픽셀마다 시간에 따른 변화를 재는 ITU 방식으로 교체 (커밋 `7a29ab1`). 시험: 면적 30%는 위험, 20%는 안전으로 구분됨
- **배운 것**: 면적 조건이 있는 기준은 픽셀 단위로 재야 한다

### A3. 해상도를 줄이면 경계 패턴의 정답이 뒤집힘 (11-08)
- **증거**: pse-test-media `25pct_screen` 패턴은 위험 25.19% / 안전 24.81%로 차이가 0.37%뿐. 1920×1080을 640×360으로 줄이자 a003(세로 줄무늬, 안전)이 **25.05%(위험)** 로 뒤집힘. 16개 중 1개
- **원인**: 3×3 픽셀이 1개로 합쳐지면서 경계선마다 생기는 반올림 오차. 줄무늬처럼 경계가 많을수록 오차가 큼
- **대응**: 경계 패턴 재현은 원래 해상도 1920×1080에서 함 (커밋 `9306c8b`, 계산: [BASICS.md](BASICS.md) §2)
- **배운 것**: 기준선 근처 시험 자료는 원본 해상도를 지켜야 한다. 노트북의 해상도 민감도 측정에서도 같은 결론(128×72에서는 줄무늬 4개 모두 놓침)

### A4. 30fps 시간 패턴을 24fps 영상에 넣으면 위험이 안전으로 바뀜 (11-09)
- **증거**: pse-test-media f021(전이 7번이 5프레임 간격) → 30fps로 재생하면 1초 최대 3.5번(위험), 24fps로 재생하면 **2.5번(안전)**
- **원인**: CSV는 프레임 번호로 쓰여 있어서, fps가 낮으면 같은 패턴이 더 긴 시간에 퍼짐. 판정기의 잘못이 아니라 합성한 영상이 실제로 달라진 것
- **대응**: pse 패턴 재현은 30fps로 함. 판정기와 오라클은 fps와 무관하게 동작 (커밋 `944285e`, [BASICS.md](BASICS.md) §5)
- **배운 것**: "판정이 fps와 무관하다"와 "합성 재료가 fps와 무관하다"는 다른 문제다

### A5. 두 프레임에 나뉜 변화를 2번으로 세어 안전을 위험으로 판정 (11-09, 노트북)
- **증거**: 실제 초당 1.88회(안전) 영상을 4.0회(위험)로 판정
- **대응**: D1(같은 방향 화면 변화는 1번). 그런데 그 직후 D3와 겹쳐 5Hz 체커보드를 10회로 세는 **새 버그**가 생겼고, 시험으로 찾아 D4로 고침 (커밋 `89daf42`, [RULES_SPEC.md](RULES_SPEC.md) §4)
- **배운 것**: 규칙 하나를 고치면 다른 경계 사례가 깨질 수 있다. 경계 시험을 먼저 만들고 고친다

### A6. 판정 규칙의 빈틈을 GAN이 공략할 수 있음 (11-09, 노트북)
- **증거**: 소프트 판정기가 반대 위상 깜빡임을 2번으로 세어 2Hz 안전 영상이 8.8(위험 목표 충족)이 됨
- **대응**: 판정기 v1(두 방향 동시 = 1번). 반대 위상에서 소프트 = 하드 (커밋 `0778e96`)
- **배운 것**: GAN의 목표가 규칙이면, 규칙의 빈틈이 곧 GAN이 찾아낼 대상이다. 규칙부터 엄밀하게

### A7. 외부 검증 일치율이 과대평가됨 (11-09, 노트북)
- **증거**: pse-test-media 210개 중 201개 일치. 하지만 142개는 화면 전이가 0인 쉬운 안전 사례이고, 기대 "위험"이 있는 세트는 3개뿐 (커밋 `d23b14e`)
- **배운 것**: 일치율만 보고하지 말고, 어려운 사례의 비율과 불일치 유형(A·B·C)을 함께 보고한다

### A8. 줄무늬 cpd 상한이 비스듬한 스캔 때문에 작동하지 않음 (11-10)
- **증거**: 10 cpd 세로 줄무늬(1~8 cpd 범위 밖)가 면적 56%로 줄무늬 판정됨. 75° 스캔에서는 주기 2 px가 약 7.7 px로 보여 2.6 cpd로 재짐 (`checks/pattern/motion_classes.md`)
- **원인**: cpd 범위를 스캔 방향마다 따로 잘랐음. 비스듬한 방향은 실제보다 낮은 cpd를 재므로 상한이 무의미해짐. 노트북 버전(1~10 cpd)에도 있던 결함
- **대응**: 픽셀마다 모든 방향 cpd 중 최댓값(= 줄에 수직인 방향)으로 상한 판정 → 2.8%
- **배운 것**: "범위 안에 있다"는 시험만 하면 이런 결함을 못 찾는다. 범위 **밖**의 정답 사례로도 시험해야 한다

### A9. 1~10 cpd를 출처 확인 없이 가져다 씀 (11-09 → 11-10)
- **증거**: 문헌 전수 조사(`docs/PATTERN_LITERATURE.md`)에서 실험·모델·표준·도구 어디에도 1~10 cpd가 없었음. 팀원 코드에서 출처 없이 들어온 값
- **대응**: EF 개정 합의문(Fisher·Wilkins 외 2026)의 1~8 cpd로 바꿈
- **배운 것**: 팀원 코드의 숫자도 출처를 확인하고 쓴다. 숫자마다 출처 등급을 붙이는 이유

## B. 진행 과정의 실패 (발표에서 "과정 개선"으로 쓸 것)

### B1. 계획이 두 갈래로 갈라짐 (11-09)
- **증거**: 집 PC의 PLAN 2판(1080p·30fps, GAN 없음, 단계별 확인)과 노트북 작업(GAN 재도입, 768×432·24fps)이 같은 저장소에 함께 존재
- **대응**: PLAN 개정 3판으로 합침. GAN·대량 생성은 보류 (커밋 `4703812`)
- **배운 것**: 작업 장소가 바뀔 때마다 PLAN.md를 먼저 확인하고, 방향을 바꾸면 PLAN.md부터 고친다

### B2. 확인 전에 다음 단계로 넘어감 (11-08)
- **증거**: 0단계 점검표를 보여준 직후, 사용자 확인 없이 1단계를 진행
- **대응**: "사용자가 통과라고 하기 전에는 다음 단계로 가지 않는다"를 PLAN 진행 규칙 1번으로 둠

### B3. 원본 영상 주소가 바뀌었는데 오류 없이 404 페이지를 받음 (11-08)
- **증거**: `BigBuckBunny_640x360.m4v`를 받았더니 146바이트 HTML("404 Not Found"). 서버가 파일을 `.zip`으로 바꿔 둔 상태였음
- **대응**: zip 주소로 바꾸고, `step0_check.py`가 받은 뒤 SHA256까지 확인하게 함 (커밋 `8e2dc37`, `f921828`)
- **배운 것**: 받은 파일은 크기와 지문으로 반드시 확인한다

### B4. 경로를 억지로 끼워 넣어 모듈을 못 찾음 (11-08)
- **증거**: `sys.path.insert`로 `src`를 끼워 넣어서 VS Code와 다른 실행 방식에서는 `lumi_synth`를 찾지 못함
- **대응**: `pip install -e .`로 정식 설치 (커밋 `0f8f713`)

### B5. 확인 없이 쓴 설정 파일이 깨져 있었음 (11-08)
- **증거**: VS Code 설정 JSON의 경로 `\\`가 쓰는 과정에서 `\`로 줄어 JSON 형식 오류. VS Code는 이 설정을 무시함
- **대응**: 경로를 `/`로 바꾸고 JSON 검사를 통과시킴
- **배운 것**: 만든 파일은 형식 검사까지 하고 "됐다"고 말한다

### B6. 실패한 명령 뒤에 삭제가 계속 실행됨 (11-08)
- **증거**: `mv`가 권한 오류로 실패했는데 스크립트가 멈추지 않아 `pse-test-media`가 함께 지워짐. 같은 커밋 `ef78542`로 다시 받아 복구
- **배운 것**: 삭제는 앞 단계 성공을 확인한 뒤 별도 명령으로 한다
